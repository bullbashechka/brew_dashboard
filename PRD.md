# Brew Dashboard — Product Requirements Document

**Версия:** MVP 1.0  
**Дата:** 2026-08-21  
**Статус:** готово к разработке  
**Язык документа:** русский; программные идентификаторы, маршруты, API и сущности БД — английские.

## 1. Назначение продукта

Brew Dashboard — закрытое адаптивное веб-приложение для владельца небольшой сети кофеен из 1–5 точек. Продукт объединяет в одном окне продажи, прибыльность, ассортимент, остатки, списания, сотрудников и смены, отзывы, сравнение точек и системные предупреждения.

MVP работает на реалистичном встроенном демо-наборе. Демо-данные разрешено полноценно создавать, редактировать, удалять и восстанавливать. Изменения сохраняются в Supabase отдельно для каждого аккаунта. Интеграции с POS, импорт и экспорт CSV отсутствуют.

### 1.1. Целевая аудитория

- один владелец небольшой сети кофеен;
- одна сеть на аккаунт;
- 1–5 точек в сети;
- один пользователь с полным доступом, без ролей и приглашений.

### 1.2. Главная пользовательская ценность

Владелец за несколько минут должен понять:

- сколько сеть заработала и как результат изменился относительно прошлого периода;
- какие точки, товары и часы дают лучший и худший результат;
- где заканчиваются запасы;
- сколько и почему списывается;
- как меняются оценки клиентов;
- какие системные проблемы требуют внимания.

### 1.3. Цели MVP

- показать полноценный end-to-end сценарий управления сетью на демо-данных;
- обеспечить согласованные финансовые и операционные показатели во всех разделах;
- дать полный ручной CRUD для демонстрации рабочих сценариев;
- обеспечить безопасный доступ по логину и паролю;
- работать на компьютере, планшете и телефоне;
- предоставить техническую основу для будущего подключения реальных источников данных без включения таких интеграций в MVP.

## 2. Границы MVP

### 2.1. Входит в MVP

## 3. Технологическая основа

Проект создаётся на основе шаблона `di-sukharev/vibe`, ветка `master`.

### 3.1. Сохраняемые части шаблона

- Bun workspace и единый monorepo;
- `webapp`: React, TypeScript, Vite, TanStack Router, TanStack Query, TanStack Form, Tailwind CSS, shadcn/ui, Recharts, Zod, Playwright;
- `backend`: Hono, Zod/OpenAPI и общая структура API, адаптированные под Cloudflare Workers;
- `packages/contracts`: общие Zod-схемы и TypeScript-типы запросов и ответов;
- lint, typecheck, unit, integration и E2E-команды.

### 3.2. Удаляемые или заменяемые части шаблона

- `website` и Astro — удалить из активных workspace;
- mobile — не подключать;
- Prisma, локальный standalone PostgreSQL и штатную схему БД шаблона — заменить Supabase migrations и типами БД;
- собственную исходную auth-модель шаблона — заменить описанной в этом PRD авторизацией по логину;
- email/password reset, роли администратора в webapp, media storage и background jobs шаблона — удалить;
- Terraform и runbook для DigitalOcean/Yandex — заменить Cloudflare deployment configuration;
- неиспользуемые зависимости и команды удалить из `package.json` и lockfile.

### 3.3. Целевая архитектура

- один Cloudflare Worker обслуживает `/api/*` через Hono и статическую сборку React/Vite;
- для неизвестных статических маршрутов используется SPA fallback на `index.html`;
- React обращается только к Hono API того же origin;
- Hono обращается к Supabase серверным publishable/secret credentials, которые хранятся только в Cloudflare Secrets;
- браузер не получает ключ с обходом RLS и не обращается к Supabase напрямую;
- контракты API определяются Zod-схемами в `packages/contracts`;
- все временные значения хранятся в UTC и отображаются в часовом поясе сети.

## 5. Глобальный интерфейс и поведение

### 5.1. Навигация

- Desktop: постоянная левая боковая панель, верхняя панель фильтров и контента.
- Tablet: сворачиваемая боковая панель.
- Mobile: компактная верхняя панель и drawer-меню; ключевые действия остаются доступны без горизонтального скролла страницы.
- В меню Alerts отображается badge с количеством непрочитанных активных предупреждений.
- Выход расположен в меню профиля.

### 5.2. Глобальные фильтры

На аналитических экранах доступны:

- точка: `All locations` или одна точка;
- период: `Today`, `Yesterday`, `7 days`, `30 days`, `This month`, `Custom range`;
- переключатель сравнения с предыдущим аналогичным периодом.

Фильтры сохраняются в URL query parameters и переживают обновление страницы. Для каждого экрана допустимы дополнительные локальные фильтры. Недоступные фильтры не показываются.

### 5.3. Правила периодов

- границы календарных дней и месяцев рассчитываются в IANA timezone сети;
- `7 days` и `30 days` включают текущий день;
- предыдущий аналогичный период имеет ту же длительность и заканчивается непосредственно перед текущим;
- `This month` сравнивается с таким же числом прошедших дней предыдущего месяца;
- `Today` сравнивается со вчерашним днём до того же локального времени;
- при делении на ноль процент изменения показывается как `N/A`, а не как бесконечность.

### 5.4. Общие состояния

Каждый экран обязан иметь:

- skeleton при первичной загрузке;
- локальный progress-state при сохранении;
- понятное empty-state с релевантным действием;
- error-state с повторной попыткой;
- toast после успешного создания, изменения, удаления, восстановления или сброса;
- подтверждение перед удалением и другими разрушительными действиями;
- защиту от повторной отправки формы;
- сохранение введённых данных при исправимой ошибке API.

## 6. Авторизация и аккаунт

### 6.1. Создание аккаунта администратором

Публичной регистрации нет. Администратор запускает защищённый CLI-скрипт:

```text
bun run admin:create-user -- --login <login>
```

Скрипт:

1. проверяет уникальность нормализованного логина;
2. принимает пароль интерактивно или генерирует криптографически стойкий пароль;
3. создаёт пользователя, профиль и рабочее пространство;
4. подготавливает исходный демо-набор;
5. выводит логин и сгенерированный пароль один раз;
6. никогда не записывает открытый пароль в БД, логи или файлы.

Требования к логину: 3–64 символа, латинские буквы, цифры, `.`, `_`, `-`; регистр при сравнении не учитывается. Требования к паролю: 12–128 символов.

### 6.2. Хранение пароля

- В БД хранится только производный ключ PBKDF2-HMAC-SHA-256, уникальная случайная соль, число итераций и версия алгоритма.
- Минимум: 600 000 итераций, соль 16 байт, результат 32 байта.
- Дополнительный pepper хранится как Cloudflare Secret и не записывается в Supabase.
- Проверка выполняется с constant-time comparison.

### 6.3. Вход и защита от перебора

- Форма содержит `login`, `password` и кнопку входа.
- Сообщение об ошибке едино: «Неверный логин или пароль»; существование логина не раскрывается.
- Разрешено не более пяти неудачных попыток за 15 минут для комбинации нормализованного логина и IP.
- После лимита API возвращает `429` и время до следующей попытки.
- IP и логин в журнале попыток хранятся в виде keyed hash, без открытого IP.
- Успешный вход очищает активный счётчик для комбинации.

### 6.4. Сессия

- Срок действия — семь суток без автоматического продления.
- Cookie: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`.
- В cookie хранится случайный 256-битный session token; в БД — только SHA-256 hash токена.
- Выход отзывает сессию в БД и удаляет cookie.
- Все mutation-запросы проверяют `Origin` и принимают только JSON с того же origin.
- Просроченная или отозванная сессия приводит к `401`, очистке локального query cache и переходу на `/login`.

### 6.5. Ограничения аккаунта

- один пользователь связан ровно с одной сетью;
- один аккаунт имеет полный доступ ко всем данным своей сети;
- пользователь не может сменить или восстановить пароль в интерфейсе;
- смену или сброс пароля выполняет только администратор отдельным CLI-скриптом;
- UI управления пользователями отсутствует.

## 7. Первый вход и onboarding

### 7.1. Последовательность

`Login → Language selection → Onboarding → Demo generation/adaptation → Overview`.

### 7.2. Выбор языка

- показывается сразу после первого успешного входа;
- варианты: English и Русский;
- English выбран по умолчанию;
- выбор обязателен и сохраняется в профиле;
- язык можно позднее изменить в Settings.

### 7.3. Поля onboarding

- название сети: обязательно, 2–80 символов;
- имя владельца: обязательно, 2–80 символов;
- количество точек: целое число от 1 до 5, значение по умолчанию — 3;
- название каждой точки: обязательно, уникально внутри сети, 2–80 символов;
- страна: обязательный ISO 3166-1 alpha-2 код;
- валюта: обязательный ISO 4217 код;
- часовой пояс: обязательный IANA timezone.

POS, среднее число заказов и средний чек в onboarding отсутствуют.

### 7.4. Завершение onboarding

- данные проверяются на клиенте и сервере;
- сеть, точки и демо-набор обновляются в одной идемпотентной операции;
- повторный запрос не создаёт дубликаты;
- при ошибке пользователь остаётся на форме и может повторить действие;
- доступ к `/app/*` до успешного завершения закрыт.

## 8. Демо-данные

### 8.1. Состав исходного набора

Базовый реалистичный профиль:

- 3 точки; генератор адаптируется к выбранным 1–5 точкам;
- данные за текущий день и предыдущие шесть месяцев;
- 25–30 товаров в нескольких категориях;
- 10–15 сотрудников, пропорционально числу точек;
- заказы и позиции заказов с утренними и дневными пиками;
- скидки, частичные/полные возвраты и отмены;
- себестоимость и цены, достаточные для расчёта маржи;
- остатки, приходы, расходы, корректировки и списания;
- смены;
- отзывы с оценками 1–5 и RU/EN-текстами;
- данные, намеренно создающие несколько low-stock, out-of-stock, inactive-location и sales-drop предупреждений;
- месячные цели выручки.

Генерация детерминирована seed-значением сети и датой генерации: повторный сброс в один день создаёт одинаковый исходный набор.

### 8.2. Даты

- При создании аккаунта и при каждом Reset даты рассчитываются относительно текущей даты в timezone сети.
- В наборе всегда есть записи для Today и Yesterday.
- После генерации новые записи автоматически по расписанию не добавляются.

### 8.3. Редактирование

Все бизнес-данные можно вручную создавать, изменять и мягко удалять. Изменения сохраняются между сессиями. Любая mutation отражается во всех зависимых показателях после успешного ответа API.

### 8.4. Reset demo data

- Кнопка находится в Settings.
- Перед сбросом показывается модальное подтверждение с точным описанием последствий.
- Сброс заменяет продажи, товары, категории, остатки, движения, списания, сотрудников, смены, отзывы, темы, предупреждения и цели исходным набором.
- Сохраняются аккаунт, логин, язык, имя владельца, название сети, страна, валюта, timezone, существующие точки и настройки интерфейса.
- Названия и количество точек сохраняются; новые данные генерируются для текущего набора точек.
- Корзина бизнес-данных и соответствующий журнал старых изменений очищаются.
- Операция транзакционная: пользователь видит либо полностью новый набор, либо прежний.
- Повторное нажатие во время выполнения блокируется.

## 9. Метрики и единые формулы

Вводимые цены считаются ценами с включённым единым налогом сети.

| Показатель | Формула |
|---|---|
| Gross sales | `Σ(quantity × unit_price)` по неотменённым позициям |
| Discounts | сумма скидок на позиции и заказ без двойного учёта |
| Refunds | фактически возвращённая клиенту сумма |
| Net sales incl. tax | `gross_sales - discounts - refunds` |
| Tax | `net_sales_incl_tax × tax_rate / (100 + tax_rate)` |
| Revenue excl. tax | `net_sales_incl_tax - tax` |
| COGS | `Σ(quantity × unit_cost_at_sale)` по неотменённым проданным позициям |
| Gross profit | `revenue_excl_tax - COGS` |
| Gross margin | `gross_profit / revenue_excl_tax × 100%` |
| Orders | завершённые, частично или полностью возвращённые заказы; отмены исключены |
| Average check | `net_sales_incl_tax / orders` |
| Waste cost | `Σ(waste_quantity × unit_cost_at_event)` |
| Goal completion | `actual_net_sales / monthly_target × 100%` |

Дополнительные правила:

- возврат уменьшает выручку, но автоматически не сторнирует COGS; для возвращённого на склад остатка создаётся отдельное inventory adjustment;
- отменённый заказ не входит в продажи, заказы, COGS и средний чек, но показывается в аналитике отмен;
- себестоимость фиксируется в позиции заказа на момент продажи, поэтому последующее изменение карточки товара не меняет историю;
- деньги хранятся как decimal/numeric, не float;
- количество может быть decimal для весовых складских единиц;
- отображение денег следует правилам выбранной ISO-валюты;
- показатели по часам группируются в timezone сети.

## 10. Функциональные требования по разделам

### 10.1. Overview

Верхняя зона содержит фиксированные KPI:

- net sales;
- orders;
- average check;
- gross profit;
- COGS;
- gross margin;
- waste cost;
- количество активных точек;
- количество активных системных предупреждений.

Каждый финансовый KPI показывает абсолютное значение, изменение к предыдущему периоду и направление изменения. Для waste рост считается негативным.

Обязательные виджеты:

- динамика продаж и gross profit;
- выполнение месячного плана сети;
- выручка и прибыль по точкам;
- top/bottom products;
- menu engineering summary;
- остатки: low/out-of-stock;
- списания по категориям;
- рейтинг и количество отзывов;
- сотрудники на сменах и суммарные часы;
- список последних критичных предупреждений.

Настройка:

- верхние KPI не скрываются;
- остальные виджеты можно скрывать, показывать и менять местами drag-and-drop;
- размеры виджетов фиксированы дизайн-системой;
- выбор сохраняется для аккаунта;
- кнопка восстановления исходного layout доступна в Settings.

Печатная версия:

- печатает текущие фильтры, период сравнения, KPI и видимые виджеты;
- скрывает навигацию, кнопки и интерактивные элементы;
- содержит название сети, дату/время формирования и timezone;
- корректно разбивает содержимое на страницы A4;
- сохранение PDF выполняется системным print dialog браузера.

Критерии приёмки:

- все KPI совпадают с едиными формулами раздела 9;
- смена точки или периода обновляет все зависимые виджеты;
- порядок и видимость сохраняются после повторного входа;
- print preview не обрезает значения и легенды.

### 10.2. Locations

Список точек отображается карточками:

- название;
- `Active`/`Inactive`;
- net sales, gross profit, orders, average check, margin;
- изменение к предыдущему периоду;
- текущий рейтинг;
- low/out-of-stock count;
- active alerts count.

Детальная страница точки повторяет основные аналитические блоки Overview, но всегда зафиксирована на одной точке, и содержит вкладки `Summary`, `Sales`, `Inventory`, `Employees`, `Reviews`.

Сравнение точек:

- пользователь выбирает 2–5 точек;
- таблица и графики сравнивают продажи, прибыль, маржу, заказы, средний чек, waste и рейтинг;
- доступна сортировка по каждому показателю;
- лучший и худший результат визуально обозначаются, но не только цветом.

Управление:

- точку можно создать, переименовать и изменить её статус;
- в сети должно оставаться минимум 1 и максимум 5 точек;
- точка с историческими данными не удаляется физически: действие переводит её в `Inactive`;
- статус `Inactive` создаёт системное предупреждение; расписание работы не используется.

### 10.3. Sales

Экран содержит:

- KPI gross sales, discounts, refunds, net sales, tax, revenue excl. tax, COGS, gross profit, margin, orders, average check;
- график продаж и прибыли по дням/часам в зависимости от диапазона;
- сравнение текущего и предыдущего периода;
- heatmap часов и дней недели;
- список peak hours;
- распределение продаж по точкам, категориям и товарам;
- таблицу заказов и позиций;
- отдельные показатели скидок, возвратов и отмен;
- фильтры по точке, товару, категории, сотруднику и статусу заказа.

CRUD:

- можно создавать и редактировать заказ и его позиции;
- заказ имеет статус `completed`, `partially_refunded`, `refunded` или `cancelled`;
- сумма возврата не может быть отрицательной или превышать оплаченную сумму после скидки;
- отмена и возврат — разные операции;
- удаление заказа мягкое и требует подтверждения;
- пересчёт итогов заказа выполняется сервером.

### 10.4. Menu / Products

Каталог содержит категории и товары. Карточка товара включает:

- название, category, optional SKU;
- selling price incl. tax;
- current unit cost;
- active/inactive status;
- продажи в штуках и деньгах;
- COGS, gross profit и margin;
- долю в выручке;
- waste quantity/cost;
- остатки по точкам.

Menu engineering matrix строится для выбранного периода:

- популярность — количество проданных единиц относительно медианы активных товаров;
- прибыльность — contribution margin на единицу относительно медианы;
- `Stars`: высокая популярность и высокая прибыльность;
- `Workhorses`: высокая популярность и низкая прибыльность;
- `Puzzles`: низкая популярность и высокая прибыльность;
- `Dogs`: низкая популярность и низкая прибыльность.

Простые рекомендации:

- Stars: поддерживать наличие и видимость;
- Workhorses: проверить цену и себестоимость;
- Puzzles: усилить продвижение и размещение;
- Dogs: пересмотреть рецепт, цену или присутствие в меню.

Рекомендации являются rule-based текстом, не используют AI и не выполняют изменения автоматически.

CRUD поддерживает категории и товары. Цена и себестоимость должны быть неотрицательными. Деактивация сохраняет историческую аналитику.

### 10.5. Inventory

Экран содержит:

- справочник складских позиций;
- остатки по каждой точке;
- единицу измерения;
- минимальный порог;
- статусы `In stock`, `Low stock`, `Out of stock`;
- краткую историю последних движений;
- фильтры по точке, статусу и позиции.

Типы движения:

- `receipt` — приход;
- `usage` — расход;
- `writeoff` — списание, связанное с Waste;
- `adjustment` — ручная корректировка.

Правила:

- остаток изменяется только через движение;
- ручное изменение видимого остатка создаёт `adjustment`;
- расход и списание вводятся положительным количеством, сервер применяет отрицательное направление;
- отрицательный остаток запрещён;
- low stock: `0 < on_hand <= min_threshold`;
- out of stock: `on_hand = 0`;
- порог задаётся отдельно для позиции и точки;
- успешное движение немедленно обновляет Inventory, Waste и Alerts.

### 10.6. Waste

Простой журнал списаний содержит:

- дату и время;
- точку;
- складскую позицию или товар;
- количество и единицу;
- себестоимость на момент события;
- стоимость списания;
- обязательную причину;
- комментарий.

Предустановленные причины: `Expired`, `Preparation error`, `Damaged`, `Overproduction`, `Other`.

Создание waste entry в одной транзакции создаёт inventory movement типа `writeoff`. Изменение или восстановление записи корректно компенсирует остаток. Удаление мягкое; остаток восстанавливается компенсирующим движением, а не изменением старой истории.

Над журналом показывается компактная сводка для текущих фильтров: total waste cost, quantity и доля waste от revenue. Отдельный расширенный аналитический экран, прогнозы и рекомендации по списаниям в MVP отсутствуют.

### 10.7. Employees / Shifts

Employees:

- имя;
- должность;
- основная точка;
- статус `Active`/`Inactive`;
- дата начала работы;
- optional contact note без чувствительных персональных данных.

Shifts:

- сотрудник;
- точка;
- start/end datetime;
- статус `Scheduled`, `Open`, `Closed`;
- optional note.

Правила:

- конец смены позже начала;
- у одного сотрудника не может быть пересекающихся смен;
- одновременно может быть только одна `Open` смена сотрудника;
- деактивированный сотрудник сохраняется в истории и не выбирается для новых смен;
- аналитика показывает количество смен, часы и распределение по точкам;
- оценка производительности и payroll отсутствуют.

### 10.8. Reviews

Экран содержит:

- average rating;
- reviews count;
- последние отзывы;
- trend рейтинга;
- распределение 1–5 звёзд;
- частые положительные и негативные темы;
- сравнение точек;
- фильтры по точке, rating, теме и периоду.

CRUD:

- rating — обязательное целое число 1–5;
- текст — 1–2000 символов;
- дата, точка и optional author label;
- отзыв можно создать, изменить, мягко удалить и восстановить.

Темы определяются без AI:

- текст нормализуется по регистру и пунктуации;
- RU/EN keyword dictionaries сопоставляют отзыв темам `Taste`, `Service`, `Speed`, `Cleanliness`, `Price`, `Atmosphere`;
- 4–5 звёзд считаются positive, 1–2 — negative, 3 — neutral;
- пользователь может вручную добавить или убрать тему у отзыва;
- ручная коррекция имеет приоритет над автоматическим сопоставлением;
- словари и темы редактируются в Reviews, изменения запускают повторную классификацию только автоматических назначений.

### 10.9. Alerts

Только системные предупреждения внутри веб-приложения:

1. `LOW_STOCK`;
2. `OUT_OF_STOCK`;
3. `LOCATION_INACTIVE`;
4. `SALES_DROP`.

Каналы email, push и messenger отсутствуют.

Правила генерации:

- low/out-of-stock рассчитываются из текущего остатка и порога;
- inactive создаётся только по ручному статусу точки;
- sales drop сравнивает продажи текущего дня до текущего локального времени со средним предыдущих четырёх таких же дней недели до того же времени;
- если четырёх периодов нет, используется доступный предыдущий аналогичный период;
- если нет ни одного полного периода для сравнения, sales-drop alert не создаётся;
- рекомендуемый порог падения по умолчанию — 30%; пользователь может менять его для сети и переопределять для точки;
- одно условие создаёт один активный alert по fingerprint; дубликаты запрещены.

Состояния: `Unread`, `Read`, `Resolved`.

- пользователь может отметить предупреждение прочитанным;
- low/out/inactive автоматически resolve после устранения причины;
- sales drop resolve после окончания локального дня или нормализации показателя;
- resolved alerts остаются в краткой истории;
- Alerts поддерживает фильтры типа, точки, статуса и даты.

### 10.10. Settings

Разделы настроек:

- `Profile`: имя владельца;
- `Network`: название сети, страна, валюта, timezone, единая налоговая ставка;
- `Locations`: названия и статусы 1–5 точек;
- `Language`: English/Русский;
- `Alert thresholds`: sales drop и low-stock overrides;
- `Revenue goals`: месячный план сети и каждой точки;
- `Overview layout`: видимость, порядок и восстановление layout;
- `Demo data`: Reset demo data;
- `History`: журнал изменений;
- `Trash`: восстановление удалённых записей;
- `Session`: выход.

Смена валюты меняет формат отображения и валюту новых записей, но не выполняет конвертацию исторических сумм. Смена timezone влияет на группировку и отображение, не меняя UTC timestamps.

## 11. Журнал изменений и корзина

Для каждой mutation фиксируются:

- timestamp;
- user ID;
- entity type и ID;
- action: `create`, `update`, `delete`, `restore`, `reset`;
- before/after JSON для изменяемых полей;
- request ID.

Правила:

- все пользовательские удаления мягкие через `deleted_at`;
- удалённые записи по умолчанию исключаются из аналитики;
- корзина показывает тип, название, дату удаления и действие Restore;
- автоматической окончательной очистки корзины в MVP нет;
- restore проверяет зависимости и уникальные ограничения;
- журнал доступен только для чтения;
- Reset очищает историю и корзину бизнес-данных, но создаёт новую запись `reset`.

- внешние ключи запрещают orphan records;
- `network_id` индексируется во всех бизнес-таблицах;
- составные индексы: `(network_id, occurred_at)`, `(network_id, location_id, occurred_at)`, `(network_id, status)` по назначению таблицы;
- денежные поля: `numeric(14,2)`; проценты: `numeric(7,4)`; количества: `numeric(14,3)`;
- timestamps: `timestamptz`;
- login, session и credential-таблицы недоступны клиентским ролям Supabase;
- RLS включён на всех таблицах, для `anon` и `authenticated` нет разрешающих policies;
- Hono использует server secret и обязательно добавляет `network_id` из проверенной сессии к каждой бизнес-операции;
- `network_id` из request body игнорируется или запрещается.

### 13.4. Ответы и ошибки

Успех:

```json
{
  "data": {},
  "meta": {},
  "requestId": "uuid"
}
```

Ошибка:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Localized user-safe message",
    "fields": {}
  },
  "requestId": "uuid"
}
```

Обязательные коды: `VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMITED`, `DEPENDENCY_CONFLICT`, `INTERNAL_ERROR`.

## 14. Валидация и транзакции

- Клиентская валидация улучшает UX, серверная является обязательной и авторитетной.
- Общие Zod-контракты используются webapp и backend.
- Все идентификаторы проверяются как UUID и на принадлежность сети текущей сессии.
- Создание/изменение заказа и его позиций — одна транзакция.
- Waste + inventory movement — одна транзакция.
- Reset demo data — одна транзакция или атомарная database function.
- Restore восстанавливает сущность и необходимые связи атомарно.
- Денежные суммы заказа и аналитические totals клиент не задаёт; их рассчитывает сервер.
- Для update используется optimistic concurrency через `updated_at` или version; конфликт возвращает `409` и предлагает обновить запись.

## 15. Локализация

- Поддерживаются `en` и `ru`.
- Английский — default и fallback.
- Все UI-тексты, validation messages, empty/error states, даты и числа локализуются.
- API возвращает стабильный machine-readable code; человекочитаемый текст формирует webapp по словарю.
- Пользовательские данные не переводятся.
- Названия маршрутов и ключи БД остаются английскими.
- Отсутствующий translation key обнаруживается тестом и в production заменяется английским значением.

## 16. Визуальная система

Тема только светлая. Стиль — современная кофейная эстетика:

- тёплый off-white фон;
- кремовые поверхности карточек;
- тёмно-коричневый основной текст;
- кофейный accent для primary actions;
- зелёный для положительных значений, янтарный для предупреждений, красный для критичных состояний;
- цвет никогда не является единственным способом передачи статуса;
- графики используют различимые и контрастные серии;
- декоративные изображения не требуются.

Компоненты строятся на shadcn/ui и существующей дизайн-системе шаблона. Интерфейс должен выглядеть профессионально и аналитически, без тяжёлой декоративности.

## 17. Responsive и accessibility

### 17.1. Breakpoints

- mobile: 320–767 px;
- tablet: 768–1279 px;
- desktop: 1280 px и выше.

На mobile:

- полная клавиатурная навигация;
- видимый focus;
- семантические landmarks и headings;
- корректные label, description и error associations;
- доступные dialogs, menus, tabs и tables;
- минимум AA contrast;
- status messages через `aria-live` без избыточного озвучивания;
- графики имеют текстовое summary и доступную табличную альтернативу;
- интерактивные цели соответствуют требованиям для touch;
- prefers-reduced-motion отключает необязательные анимации.

## 18. Производительность

Цели измеряются на типичном production-наборе MVP и обычном мобильном интернете:

- первый полезный экран — не более 3 секунд;
- переходы и применение фильтров — не более 1 секунды после получения ответа;
- сохранение mutation — не более 2 секунд для p95 без учёта сетевого отказа;
- API analytics p95 — до 800 мс;
- CRUD API p95 — до 500 мс;
- таблицы используют server pagination, а длинные списки — виртуализацию при необходимости;
- TanStack Query кэширует read-запросы и инвалидирует только затронутые query keys;
- route-level code splitting обязателен;
- графики не блокируют первичное отображение KPI.

## 19. Безопасность

- все соединения только HTTPS;
- секреты только в Cloudflare Secrets и локальных uncommitted env-файлах;
- открытые пароли, session tokens и service keys не логируются;
- service key Supabase не попадает в Vite env;
- every API query scoped by session-derived `network_id`;
- CORS ограничен production origin; same-origin deployment является нормой;
- security headers: CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy`, frame protection;
- JSON body size ограничен 1 MiB;
- Zod stripping/rejection неизвестных полей для mutation;
- database constraints дублируют критичные проверки;
- audit log не хранит password fields и session tokens;
- login rate limiting реализован приложением;
- зависимости проверяются `bun audit` перед релизом.

## 20. Наблюдаемость

Используется только Cloudflare Workers Observability:

- structured JSON logs;
- поля `requestId`, route, method, status, durationMs, userId, networkId;
- credential values, request passwords, cookies и полные review texts не логируются;
- ошибки API содержат stack только в server logs, не в ответе;
- отслеживаются 5xx rate, latency, login failures, rate limits и demo reset failures;
- React показывает пользователю безопасную ошибку и request ID для диагностики;
- отдельный клиентский error collector и Sentry отсутствуют.

## 23. Разработка и миграции

- локальная БД запускается через Supabase CLI;
- изменения схемы создаются versioned SQL migrations в `supabase/migrations`;
- demo generator и минимальные test fixtures версионируются в репозитории;
- TypeScript database types генерируются из схемы и проверяются в CI;
- миграции применяются до новой версии Worker;
- миграции должны быть backward-compatible с текущим production Worker на время ручного релиза;
- destructive schema changes выполняются expand/migrate/contract, не одной необратимой миграцией.

## 24. Production deployment

В MVP существует только одно облачное окружение:

- один Cloudflare Worker для API и static assets;
- один Supabase production project;
- один production URL;
- автоматические preview и staging отсутствуют.

Cloudflare configuration:

- `/api/*` всегда обрабатывается Worker;
- static assets обслуживаются Cloudflare;
- `not_found_handling = "single-page-application"`;
- compatibility date зафиксирована в репозитории;
- Workers Observability включён;
- Supabase URL, server key, password pepper и session secret находятся в Cloudflare Secrets.

Релиз ручной и разрешён только при:

1. чистом git worktree;
2. успешных lint, typecheck, unit, integration и E2E;
3. успешном production build;
4. применённых миграциях Supabase;
5. smoke-check `/api/v1/health`;
6. smoke-check login и Overview после `wrangler deploy`.

## 25. End-to-end критерии готовности MVP

MVP считается готовым, когда одновременно выполнено следующее:

- администратор одной CLI-командой создаёт login/password аккаунт без хранения открытого пароля;
- пользователь входит, выбирает язык, проходит onboarding и видит реалистичный dashboard;
- каждый раздел из навигации реализован и работает на общих данных;
- все глобальные периоды, location filter и previous-period comparison согласованы;
- financial metrics совпадают между Overview, Locations, Sales и Products;
- полный CRUD доступен для бизнес-данных;
- soft delete, audit log, trash и restore работают;
- low stock, out of stock, inactive location и sales drop создаются и resolve по правилам;
- настройка thresholds, revenue goals, language и widget order сохраняется;
- Reset создаёт актуальный шестимесячный набор и сохраняет профиль/настройки/точки;
- Overview корректно печатается и сохраняется в PDF через браузер;
- интерфейс полностью работает на desktop, tablet и mobile;
- основные journeys проходят в поддерживаемых браузерах;
- WCAG 2.2 AA требования выполнены для критичных сценариев;
- performance targets раздела 18 выполнены;
- production развернут как один Cloudflare Worker с Supabase;
- в продукте отсутствуют публичная регистрация, CSV, POS, внешние интеграции, сторонние уведомления, AI, dark mode и публичный сайт.

Фича завершена только если:

- реализованы desktop, tablet и mobile states;

- клиентская и серверная Zod-валидация согласованы;
- все запросы изолированы по `network_id` текущей сессии;
- mutation создаёт audit entry;
- локализация en/ru полная;
- клавиатурная навигация и screen-reader labels проверены;

- критичный пользовательский путь покрыт Playwright;
- typecheck, lint и полный согласованный test suite проходят;
- документация API и schema migration обновлены;
- секреты и персональные данные не попадают в код, логи и тестовые fixtures.
